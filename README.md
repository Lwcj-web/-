## 1. 为什么做这个

赛题要求"AI 代人操作银行"，同时把安全合规设为 30% 权重、一票否决。这两句话放在一起，指向的其实是一个工程难题：

**当 Agent 拿到了账户的操作权，安全就不能是事后提醒，必须是执行前的强制闸门。**

大多数方案把安全做成"风险提示气泡"，用户点"我知道了"就能绕过。FinGuard 的做法是把安全做进执行链路本身——每一笔操作必须依次穿过五道闸门，任何一道不通过就物理上无法落地。这不是产品话术，是代码结构决定的。

## 2. 五道防线

```
用户输入（自然语言 / 语音）
        │
   ┌────▼─────────────────────────────────────────┐
   │ L1  提示注入防御    InjectionGuard            │
   │     11 条规则族 + 零宽字符 + 控制符 + 超长输入  │
   └────┬─────────────────────────────────────────┘
        │ 净化后的文本
   ┌────▼─────────────────────────────────────────┐
   │ L2  意图解析        IntentParser              │
   │     受限语法 · 槽位抽取 · 未知即拒答 · 歧义澄清 │
   └────┬─────────────────────────────────────────┘
        │ 结构化 Action {scene, payee, amount, ...}
   ┌────▼─────────────────────────────────────────┐
   │ L3  权限分级 ABAC   PolicyEngine              │
   │     角色 × 场景等级(R0-R3) × 单笔额度 × 日累计  │
   │     × 会话熔断状态                            │
   └────┬─────────────────────────────────────────┘
        │
   ┌────▼─────────────────────────────────────────┐
   │ L5  双智能体审查    CrossExaminer             │
   │     业务经理（促成交） ∥ 风控官（保安全）      │
   │     风控官一票否决，业务经理无权覆盖            │
   └────┬─────────────────────────────────────────┘
        │
   ┌────▼─────────────────────────────────────────┐
   │ L4  幻觉防护        GroundingGuard            │
   │     回复中每个数字必须能溯源到交易台账          │
   │     数值只能经模板占位符注入，禁止模型自由生成   │
   └────┬─────────────────────────────────────────┘
        │
   ┌────▼─────────────┐
   │  Executor 落库    │ → AuditLog 哈希链（不可篡改）
   └──────────────────┘
```

**关于 L4 和 L5 的顺序**：代码里 L5 先于 L4，是因为 L4 校验的对象是"即将对用户说出口的回复"，必须等风控结论确定后才能组装文案。给评委讲解时按 L1→L4→L5 走更顺，实际执行顺序见 `src/engine.js` 的 `runPipeline()`。

### 各层设计要点

**L1 注入防御**
覆盖 6 类攻击面：指令覆盖、角色劫持、提示词套取、分隔符注入、越权提权、编码规避。额外处理零宽字符（`\u200B-\u200D` 等）夹带、控制字符、超长输入、中英混写变体。

关键取舍：**规则只做"拦截"不做"改写"**。不试图把恶意输入"净化成善意输入"，因为改写本身就会引入新的攻击面。命中即拒，并向用户说明原因。

**L2 意图解析**
不用自由生成式 NLU，用受限语法 + 同义词表 + 槽位抽取器。设计原则是**宁可失败，不可猜错**：

- 缺槽位 → 返回 `missing` 列表，追问，不默认补值
- 未知意图 → `UNKNOWN_INTENT`，明确告知只支持六类业务
- 多收款人 → `AMBIGUOUS_PAYEE`，要求澄清
- 超上限金额 → 拒绝，不静默截断

这也是一种幻觉防护：把"模型自己编一个合理答案"的可能性从源头掐掉。

**L3 权限分级 ABAC**
主体 × 资源 × 操作 × 环境四元组决策：

| 角色 | 最高场景等级 | 单笔上限 |
|---|---|---|
| 户主 | R3 | 20 万 |
| 家庭成员 | R2 | 5 千 |
| 只读访客 | R0 | 0 |

| 场景等级 | 含义 | 示例 |
|---|---|---|
| R0 | 只读 | 账单查询、产品浏览 |
| R1 | 低危写 | 取消订阅、调整限额 |
| R2 | 资金变动 | 转账、申购、赎回 |
| R3 | 高额/不可逆 | 卡片挂失、开户 |

R2 及以上强制二次认证，不可直接放行。

**L5 双智能体审查**
这不是"多调一次模型"的噱头，而是把银行真实的"业务口 vs 风控口"制衡关系做成代码：

- 业务经理：负责把事办成，只能附加条件（NOTE），**不能否决风控结论**
- 风控官：独立规则集，有**一票否决权**（VETO）

风控官规则（`R-01`~`R-07`）包括涉诈话术库命中、新收款人大额、凌晨大额、老年账户向陌生账户转出、超出风险测评等级申购等。

**L4 幻觉防护**
核心机制：**数字不可自由生成**。所有数值必须通过 `GroundingGuard.fill(tpl, values)` 的占位符注入，返回值同时给出 `evidence` 数组；`verify(text, evidence)` 反向校验回复中每个数字是否在证据集内，不被支持的数字会被标记。

模板缺参数时**直接抛异常**，而不是填入 `undefined` 或空值——静默生成是幻觉的主要来源。

**审计链**
每条判定记录都带上一条记录的哈希（`prev`），形成链式结构。`verifyChain()` 可检测任意位置的篡改。演示用的哈希是 djb2 变体（浏览器无同步 SHA-256），**生产环境应替换为 SHA-256 + 可信时间戳 + 独立存储**，这一点在安全自评报告中已如实标注。

## 3. 赛题六大场景覆盖 + 两项自建能力

赛题要求的六个场景全部落地；在此之上补了两个「智能体真的该做、但赛题没点名」的能力。补它们不是为了凑数，而是因为**预算和储蓄计划是同一套管线最好的压力测试**：前者只动规则不动钱（R1），后者是真实的资金划转（R2）却不像转账那样有收款人，两级权限的差异在这里最容易暴露设计漏洞。

| 场景 | 实现要点 |
|---|---|
| **智能转账** | 人名/手机号/备注三种寻址；定时转账（周期+日期） |
| **账单分析** | 类别统计+占比条；一周花销节奏；异常识别（凌晨大额、境外商户、免密大额、重复扣款） |
| **理财操作** | 风险测评等级驱动；按适当性过滤不可售产品；一键申购/赎回；超等级申购被否决 |
| **卡片管理** | 卡申请（虚拟卡即时开立）、限额调整（前后对比回单）、冻结/解锁、挂失 |
| **订阅/代扣** | 从台账与代扣协议自动识别订阅；7 天内续费提醒；闲置订阅提示；一键取消并显示年节省 |
| **跨场景联动** | 生日场景四步编排：资金锁定 → 商户比价 → 定时下单 → 支付守门（白名单校验） |
| **预算管理**（自建） | 分类额度 R1 级；执行情况**永远从台账实时推导**，不建第二套账；上调预算触发 R-09 复核 |
| **储蓄计划**（自建） | 目标分账 R2 级；自动转入；提前支取触发 R-08 违约金判定，与 R-07 赎回同构但独立 |

两个自建能力的权限分级刻意做成不对称，这是可以直接演示的：

| 操作 | 场景等级 | 只读访客 | 家庭成员 | 户主 |
|---|---|---|---|---|
| 查看预算 / 查看储蓄计划 | R0 | 放行 | 放行 | 放行 |
| 调整预算额度 | R1 | **拒绝** | 放行 | 放行 |
| 新建 / 支取储蓄计划 | R2 | 拒绝 | 二次认证（≤5千） | 二次认证 |

## 5. 运行

**演示应用**：用 Chrome / Edge 打开 `index.html`，无需安装、无需服务器、无网络请求。

**测试报告（浏览器）**：打开 `tests.html`

**本地服务器**（录制演示视频时需要，因为录制器要通过 HTTP 回调截图接口）：

```bash
node tools/serve.js            # → http://127.0.0.1:7788/
```

**命令行测试**（三套，共 121 条断言）：

```bash
node tests/run.js        # 单元测试   64 条：覆盖五道防线 + 审计链 + 端到端
node tests/e2e.js        # 流程模拟   31 条：三角色 × 全场景，验证裁决分支正确
node tests/dom.test.js   # DOM 集成   26 条：jsdom 真实加载页面，验证渲染与交互
node tools/dryrun.js     # 分镜预演   10 步：用 jsdom 跑一遍演示脚本每一步是否可达
node tools/shoot.js      # 重录文档用图（需本机 Edge，输出到 media/screens）
```

预期输出：

```
总计 64 条：通过 64，失败 0，通过率 100.0%
流程模拟：31 条，通过 31，失败 0
DOM 集成测试：26 条，通过 26，失败 0
预演：10 步，通过 10，失败 0
```

`tests/dom.test.js` 需要 `jsdom`（仅测试依赖，主程序仍零依赖）。未安装时会自动跳过而非报错。

## 8. 已知边界（写在前面比藏起来好）

1. **NLU 是规则实现**，对高度口语化、方言、长句嵌套的鲁棒性有限。生产环境建议前置小模型做意图分类，规则层保留为可解释的兜底与校验。当前选择规则实现，是为了让每一条判定都能对评委讲清楚"为什么"。
2. **哈希是 djb2 变体**，仅用于演示链式完整性，不具备抗碰撞强度。生产替换为 SHA-256。
3. **数据为确定性伪随机生成**（种子 20251102），不涉及任何真实用户信息，符合大赛原创与合规要求。
4. **二次认证是模拟实现**（点击确认即视为通过），真实系统应对接活体检测 + 交易密码 + 设备指纹。
5. **L4 只校验数字**，未覆盖语义层面的"正确但误导"表述（如选择性呈现）。这是后续可扩展方向。
6. **`recorder.js` 只在 `?rec=1` 时加载**，线上路径不会请求该文件；它用合成事件驱动界面，因此录制出的画面是真实交互而非拼接。但它也会让"人手会有的犹豫"消失，所以旁白里不含任何"实时演示"承诺——录播就是录播。

## 9. 界面设计说明

界面不是「套个好看的主题」，它承担一个具体任务：**让用户看见自己是如何被拒绝的。**

- **五层管线做成常驻栏**，而不是弹窗日志。管线在跑时逐层高亮，未执行到的层显示「待命」，被拦下的层标红——「到哪一层停下」一眼可见。这是本产品与普通聊天机器人最直观的差别。
- **资产结构与风险态势常驻右侧**，数据全部由台账推导（环比、预算使用率、异常笔数、闲置订阅），没有「风险评分 87 分」这类编出来的指标——那本身就是一种幻觉。
- **二次认证做成三步式**（五层校验 → 二次认证 → 执行落库），并给出三个认证方式的真实交互（动态口令自动跳格、人脸、短信），而不是一个「确认」按钮打发掉。
- 账户条的余额下方给出**构成关系**（含储蓄占用 / 可用余额），而不是一个孤立的大数字。

配色用的是银行可信度色系（深蓝主色 + 中性灰底），所有颜色定义在 `:root` 里，改一处即可整体换肤。

### 本轮改动带来的两个真实缺陷（已修，并已写入测试）

这两个都不是「写完就发现有 bug」，而是**跑测试和看截图才暴露的**，记录在此以示可复现：

1. **新增场景 `goalList` 忘了登记等级**，`PolicyEngine` 用 `SCENE_LEVEL[scene] || 'R2'` 兜底，导致「查看心愿计划」这种纯只读操作被要求二次认证。兜底本身是对的（未知场景按最严处理），错的是场景名与等级表脱节。已补一条 **「所有已知场景名都必须能查到等级，只读类必须是 R0」** 的用例守住这个接缝。
2. **分类预算额度是拍脑袋写的**，而台账里真实购物支出是 ¥4,737，导致预算一打开就是 281% 超支、四项全红，看起来像系统算错。改成由种子台账「近 30 天实际 × 1.05」自动建议，演示首屏落在 68%–83% 的合理区间。

## 10. 技术栈

零依赖。原生 JavaScript + CSS，无构建步骤，无外部 CDN 请求。

选它的理由是演示环境不可控：决赛现场网络可能有波动，评委本地打开也可能没有网。一个双击就能跑、断网也能跑的作品，比一个需要 `npm install` 的作品更适合这个场景。

测试链路额外依赖 `jsdom`（仅 devDependency，不参与运行）。
