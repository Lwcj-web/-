## 3. README（正文）

> 仓库根目录的 `README.md` 与本节省略号之外的内容一致。此处按评委阅读顺序重排。

### 3.1 一句话定位

**不是“会办事的银行机器人”，而是每一次代操作都留下可解释、可否决、可审计证据链的银行智能体。**

**创作理念**：赛题要求“AI 代人操作银行”，同时把安全合规设为 30% 权重、一票否决。这两句话放在一起，指向的是一个工程难题——**当 Agent 拿到了账户的操作权，安全就不能是事后提醒，必须是执行前的强制闸门。**

大多数方案把安全做成风险提示气泡，用户点“我知道了”就能绕过。FinGuard 的做法是把安全写进执行链路本身：每一笔操作必须依次穿过五道闸门，任何一道不通过，物理上无法落地。这不是产品话术，是代码结构决定的——`runPipeline()` 里每层 `deny` 直接 `return`，没有“跳过校验”的分支。

### 3.2 五道防线

```
用户输入（自然语言 / 语音）
        │
   ┌────▼─────────────────────────────────────────┐
   │ L1  提示注入防御    InjectionGuard            │
   │     11 条规则族 + 零宽字符 + 控制符 + 超长输入  │
   └────┬─────────────────────────────────────────┘
        │ 净化后的文本
   ┌────▼─────────────────────────────────────────┐
   │ L2  意图解析        IntentParser              │
   │     受限语法 · 槽位抽取 · 未知即拒答 · 歧义澄清 │
   └────┬─────────────────────────────────────────┘
        │ 结构化 Action {scene, payee, amount, ...}
   ┌────▼─────────────────────────────────────────┐
   │ L3  权限分级 ABAC   PolicyEngine              │
   │     角色 × 场景等级(R0-R3) × 单笔额度 × 日累计  │
   │     × 会话熔断状态                            │
   └────┬─────────────────────────────────────────┘
   ┌────▼─────────────────────────────────────────┐
   │ L5  双智能体审查    CrossExaminer             │
   │     业务经理（促成交） ∥ 风控官（保安全）      │
   │     风控官一票否决，业务经理无权覆盖           │
   └────┬─────────────────────────────────────────┘
   ┌────▼─────────────────────────────────────────┐
   │ L4  幻觉防护        GroundingGuard            │
   │     回复中每个数字必须能溯源到交易台账         │
   │     数值只能经模板占位符注入，禁止模型自由生成 │
   └────┬─────────────────────────────────────────┘
        │
   ┌────▼─────────────┐
   │  Executor 落库   │ → AuditLog 哈希链（不可篡改）
   └──────────────────┘
```

**关于 L4 与 L5 的编号顺序**：代码里 L5 先于 L4 执行，因为 L4 校验的对象是“即将对用户说出口的回复”，必须等风控结论确定后才能组装文案。讲解时按 L1→L4→L5 更顺，实际执行顺序见 `src/engine.js` 的 `runPipeline()`。

| 层 | 设计要点 | 关键取舍 |
|---|---|---|
| L1 注入防御 | 覆盖 6 类攻击面：指令覆盖、角色劫持、提示词套取、分隔符注入、越权提权、编码规避；额外处理零宽字符夹带、控制字符、超长输入、中英混写变体 | 规则只做“拦截”不做“改写”——改写本身会引入新攻击面，命中即拒并说明原因 |
| L2 意图解析 | 不用自由生成式 NLU，用受限语法 + 同义词表 + 槽位抽取 | 宁可失败不可猜错：缺槽位追问、未知意图拒答、多收款人澄清、超限拒绝 |
| L3 权限分级 | 主体 × 资源 × 操作 × 环境四元组；角色天花板 × 场景等级 × 单笔额度 × 日累计 × 熔断状态 | R2 及以上强制二次认证，不可直接放行；未知场景按最严兜底 |
| L5 双智能体 | 业务经理只能附加条件（NOTE），风控官独立规则集 R-01~R-09，有一票否决权（VETO） | 把银行真实的“业务口 vs 风控口”制衡关系做成代码，不是“多调一次模型”的噱头 |
| L4 幻觉防护 | 数值只能经 `fill(tpl, values)` 占位符注入，同时产出 `evidence`；`verify(text, evidence)` 反向校验每个数字 | 模板缺参数直接抛异常，不填 `undefined`——静默生成是幻觉的主要来源 |

**权限分级矩阵**

| 角色 | 最高场景等级 | 单笔上限 |
|---|---|---|
| 户主 | R3 | 20 万 |
| 家庭成员 | R2 | 5 千 |
| 只读访客 | R0 | 0 |

| 场景等级 | 含义 | 示例 |
|---|---|---|
| R0 | 只读 | 账单查询、产品浏览、看预算 |
| R1 | 低危写 | 取消订阅、调整限额、改预算额度 |
| R2 | 资金变动 | 转账、申购、赎回、储蓄计划 |
| R3 | 高额/不可逆 | 卡片挂失、开户、办虚拟卡 |

**审计链**：每条判定记录带上一条的哈希（`prev`），形成链式结构，`verifyChain()` 可检测任意位置篡改。演示用哈希为 djb2 变体（浏览器无同步 SHA-256），**生产环境应替换为 SHA-256 + 可信时间戳 + 独立存储**，此点已在安全自评报告中如实标注。

### 3.3 赛题六大场景 + 两项自建能力

赛题要求的六个场景全部落地；在此之上补了预算管理与储蓄计划。补它们不是为了凑数，而是因为**这两条业务是同一套管线最好的压力测试**：预算只动规则不动钱（R1），储蓄计划是真实资金划转（R2）却不像转账那样有收款人，两级权限的差异在这里最容易暴露设计漏洞。

| 场景 | 实现要点 |
|---|---|
| 智能转账 | 人名 / 手机号 / 备注三种寻址；定时转账（周期 + 日期） |
| 账单分析 | 类别统计 + 占比条；一周花销节奏；异常识别（凌晨大额、境外商户、免密大额、重复扣款） |
| 理财操作 | 风险测评等级驱动；按适当性过滤不可售产品；一键申购 / 赎回；超等级申购被否决 |
| 卡片管理 | 虚拟卡即时开立；限额调整（前后对比回单）；冻结 / 解锁；挂失 |
| 订阅 / 代扣 | 从台账与代扣协议自动识别订阅；7 天内续费提醒；闲置订阅提示；一键取消并显示年节省 |
| 跨场景联动 | 生日场景四步编排：资金锁定 → 商户比价 → 定时下单 → 支付守门（白名单校验） |
| 预算管理（自建） | 分类额度 R1 级；执行情况永远从台账实时推导，不建第二套账；上调预算触发 R-09 复核 |
| 储蓄计划（自建） | 目标分账 R2 级；自动转入；提前支取触发 R-08 违约金判定 |

两个自建能力的权限分级刻意做成不对称，现场可直接演示：

| 操作 | 场景等级 | 只读访客 | 家庭成员 | 户主 |
|---|---|---|---|---|
| 查看预算 / 查看储蓄计划 | R0 | 放行 | 放行 | 放行 |
| 调整预算额度 | R1 | **拒绝** | 放行 | 放行 |
| 新建 / 支取储蓄计划 | R2 | 拒绝 | 二次认证（≤5 千） | 二次认证 |

### 3.4 已知边界（写在前面比藏起来好）

1. **NLU 是规则实现**，对高度口语化、方言、长句嵌套的鲁棒性有限。生产环境建议前置小模型做意图分类，规则层保留为可解释的兜底与校验。当前选规则实现，是为了让每一条判定都能讲清楚“为什么”。
2. **哈希是 djb2 变体**，仅用于演示链式完整性，不具备抗碰撞强度。生产替换为 SHA-256。
3. **数据为确定性伪随机生成**（种子 20251102），不涉及任何真实用户信息。
4. **二次认证是模拟实现**（点击确认即视为通过），真实系统应对接活体检测 + 交易密码 + 设备指纹。
5. **L4 只校验数字**，未覆盖语义层面的“正确但误导”表述（如选择性呈现）。这是后续可扩展方向。
6. **`recorder.js` 只在 `?rec=1` 时加载**，线上路径不会请求该文件；它用合成事件驱动界面，因此录出的画面是真实交互而非拼接。

### 3.5 界面设计说明

界面不是“套个好看的主题”，它承担一个具体任务：**让用户看见自己是如何被拒绝的。**

- 五层管线做成**常驻栏**，而不是弹窗日志。管线跑时逐层高亮，未执行到的层显示“待命”，被拦下的层标红——“到哪一层停下”一眼可见。这是本产品与普通聊天机器人最直观的差别。
- 资产结构与风险态势**常驻右侧**，数据全部由台账推导（环比、预算使用率、异常笔数、闲置订阅），没有“风险评分 87 分”这类编出来的指标——那本身就是一种幻觉。
- 二次认证做成**三步式**（五层校验 → 二次认证 → 执行落库），给出三种认证方式的真实交互（动态口令自动跳格、人脸、短信），而不是一个“确认”按钮打发掉。

## 4. 部署说明

### 4.1 运行环境

### 4.2 方式 A · 本地直接打开（推荐，30 秒）

**Nginx**

```nginx
server {
    listen 80;
```
