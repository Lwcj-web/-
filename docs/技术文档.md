# FinGuard 技术文档

**2026 第八届深圳国际金融科技大赛 · 人工智能赛道（国内）· 银行 AI 智能体**

---

## 1. 赛题理解与方案定位

赛题原文要求构建"通过对自然语言对话理解用户金融意图、自主规划并执行银行业务操作"的系统，并明确"聚焦 AI 代人操作银行（安全 + 体验）"。

关键词是"代人操作"。一旦 Agent 拥有账户操作权，它与普通助手的本质区别就出现了：**普通助手说错了话，用户还能判断；银行 Agent 做错了事，钱已经出去了。**

因此本方案没有把安全当作附加模块，而是把它作为执行链路的结构本身。这就是 FinGuard 与"功能齐全的对话式银行"最根本的分野。

### 1.1 三个核心设计主张

**主张一：安全在执行链路里，不在提示气泡里**

市面上大量方案的安全是"风险提示 + 用户点确认"。这种设计的失效点是：用户在被诈骗状态下，点确认的动作恰恰是被诱导出来的。FinGuard 的做法是**硬边界不可协商**——角色天花板、额度上限、涉诈话术命中，这三类是代码层面的 deny，用户怎么说都无法通过。

**主张二：可解释优先于覆盖率**

注入防御用规则而非模型判断，NLU 用受限语法而非自由生成。代价是覆盖面窄一些，收益是**每一句判定都能对用户、对审计、对监管讲清楚"为什么"**。金融场景的这个取舍，我认为是正确的。

**主张三：五道串联闸门 > 一个强大检测器**

串联系统的失效概率是各层失效概率之积。即使某一层被绕过，资金仍被后续层拦下。这是纵深防御的工程化表达。

|---|---|---|---|

## 3. 核心算法与实现

### 3.1 L1 注入检测

```js
inspect(raw) → { clean, hits[], verdict }
```

流程：

1. 统计零宽字符（`\u200B-\u200D`, `\u2060`, `\uFEFF`, `\u00AD`），数量 > 0 即计入 `INJ-08`，并从文本中剔除
2. 逐条规则匹配（长句用 `match`，取首个命中片段存入 `detail`）
3. 检测关键动词被分隔（`转-账` 形式）
4. 长度超限、控制字符检测
5. 汇总 verdict：任一 `block` 级命中 → `block`；仅 `warn` → `warn`；无命中 → `pass`

**为什么用 `verdict` 三值而不是布尔**：`warn` 级（如超长输入、人格渗透）不应直接拒绝正常用户，但需要留痕。三值让 UI 可以差异化呈现。

### 3.2 L2 意图解析

```js
parse(raw, ctx) → { ok, intent, slots, missing, reason?, hint? }
```

**意图判定采用"句式优先"策略**：

```js
// 转账句式优先判定，避免"给妈妈买礼物花了 500"被误判
if (/(给|向|转给|打给)\s*[\u4e00-\u9fa5]{2,4}.{0,6}(转|汇|付|打)\s*\d/.test(text)) return 'transfer';
```

之后才走同义词表。这是被测试用例逼出来的改进：纯同义词表会把"给妈妈和王大川转账 500"漏判。

**槽位抽取的坑**：

- 金额：`1.5万` / `3千` / `2k` 三种单位；且必须排除手机号中的数字（先替换手机号为占位符再匹配）
- 收款人：手机号优先；中文姓名用非贪婪匹配 `[\u4e00-\u9fa5]{2,4}?` + 前瞻断句
- 歧义：正则无法可靠切分"给妈妈和王大川"（会把"妈妈和王大川"整体当作名字），因此增加并列结构兜底匹配

**拒绝清单**（这是幻觉防护的第一道防线）：

| reason | 触发条件 | 话术 |
|---|---|---|
| UNKNOWN_INTENT | 无任何意图关键词命中 | 告知只支持八类业务 |
| AMBIGUOUS_PAYEE | 检测到多个收款对象 | 要求明确 |
| AMOUNT_OUT_OF_RANGE | > 100 万 | 引导至柜台 |
| 缺槽位 | 缺收款人或金额 | 追问，不补默认值 |

### 3.3 L3 权限决策

```js
evaluate(subject, action, ctx) → { decision, level, code, reasons[], reason }
```

决策即 §2 的五步短路。核心数据结构：

```js
SCENE_LEVEL = { bill:'R0', ..., transfer:'R2', cardLost:'R3' }
ROLE_CAPS   = { owner:{level:3, maxAmount:200000}, family:{level:2, maxAmount:5000}, ... }
```

**为什么场景等级用字符串 `R0-R3` 而非数字**：审计日志里 `level: 'R2'` 比 `level: 2` 更可读，且能直接对应监管口径的风险分级表述。

### 3.4 L5 双智能体审查

```js
cross(action, ctx, tx) → { verdict, risk, biz, ts }
```

- `riskOfficer()`：7 条规则（R-01 ~ R-07），独立于业务判断
- `businessManager()`：只产出附注（NOTE），不参与否决
- `cross()`：**风控 VETO 直接决定最终 VETO**，业务经理无权覆盖

规则表：

| 编号 | 条件 | 级别 |
|---|---|---|
| R-01 | 备注/收款人命中涉诈话术库 | VETO |
| R-02 | 新收款人且金额 ≥ 3000 | 附条件 |
| R-03 | 单笔 ≥ 20000 | 附条件 |
| R-04 | 凌晨 0–6 点且 ≥ 1000 | 附条件 |
| R-05 | 老年账户向陌生账户 ≥ 2000 | VETO |
| R-06 | 产品风险 > 用户测评等级 | VETO |
| R-07 | 持有不足 7 天赎回 | 警示 |

**R-05 的设计意图**：单独看"老年账户"不是风险，单独看"陌生人"也不是，但**组合起来就是冒充公检法/养老诈骗的高发特征**。单变量规则抓不到这种模式，组合条件可以。

### 3.5 L4 幻觉防护

```js
fill(tpl, values) → { text, evidence }
verify(text, evidence) → { ok, unsupported[], total }
```

`fill` 用 `{A}` `{B}` 占位符 + 严格参数校验（缺失即抛错）。`verify` 反向抽取数字，逐个在 `evidence` 中查找，容忍四舍五入误差。

**时间窗口同样走占位符**：账单回复模板是 `近 {G} 天共支出 {A} 元……`，连"30 天"这个数字都由 `G: 30` 注入。否则 `verify` 会把"近 30 天"里的 30 判为无出处数字，L4 永远标黄——这个坑是照着真实回复文本写用例时抓出来的（见 §6.3）。

转账回单的金额与余额同样经 `fill` 注入并过 `verify`（`转账已完成，已实时到账。金额 ¥{A} 元，当前余额 ¥{B} 元。`），流水号等非数值字段放在卡片里不进校验。这样演示转账时 L4 也是真实点亮的，而不是装饰性的"待命"。

### 3.6 审计链

```js
append(evt) → { seq, ts, prev, hash, ...evt }
verifyChain() → { ok, count } | { ok:false, seq }
```

哈希覆盖除 `hash` 字段外的全部内容，包含 `prev`。因此改内容、改 `prev`、删记录都会导致断裂。

## 4. 数据设计

### 4.1 确定性种子

```js
mulberry32(20251102)   // 固定种子，每次生成同一份数据
```

意义：**任何人打开应用看到的是同一个账户**。这不是细节，而是让技术文档里的所有示例数字（如"共支出 X 元"）在评委复现时能对上。

数据规模：90 天流水 ≈ 230 笔，含 7 类商户、3 种支付渠道、5 笔预埋异常样本。

### 4.2 预埋异常样本（供账单分析演示）

| 样本 | 特征 | 用途 |
|---|---|---|
| 某游戏平台 4980 元 | 凌晨 3:17，免密支付 | 演示时段+渠道异常 |
| 跨境商户 2680 元 | 凌晨 2:41，境外线上 | 演示地域异常 |
| 直播间打赏 1888 元 | 23:52 | 演示夜间冲动消费 |
| 视频会员 25 元 × 2 | 间隔 120 秒，同一商户 | 演示重复扣款识别 |

### 4.3 订阅自动识别

真实系统从"代扣协议表"获取，本实现模拟该表 + 从台账特征推断（`channel === '代扣'` 或商户名含会员/订阅关键词）。含 1 项标记为 `dormant`（40 天未使用）用于演示"闲置订阅清理"。

## 5. UI 设计

### 5.1 右侧「安全管线实时追踪」的意义

这是整个作品最关键的一个设计决策。银行 Agent 的安全能力，如果没有可视化，对用户就是不可见的黑盒——用户只能选择"相信"或"不信"。

管线面板把每一次请求的五层判定结果实时展开，包括命中的规则编号、权限等级、校验数字个数。这让安全从"声称具备"变成"可当场验证"。

答辩时的反差演示就在这一块：同一句话，切换主体后 L3 从"放行"变"拒绝"，颜色从绿变红。

### 5.2 逐层动画节奏

```js
setTimeout(() => walk(i + 1), 110);   // 每层间隔 110ms
```

110ms 是刻意的：太快人眼来不及看清哪一层变色，太慢会让操作显得卡顿。这个数值来自实际调节，不是随意取值。

### 5.3 顶部三个面板

- **对话**：主界面
- **安全控制台**：规则配置清单 + 运行指标（拦截数、认证数）
- **审计流水**：哈希链可视化 + 完整性校验入口

## 6. 测试策略

### 6.1 为什么测试用例是必交材料而非附加项

初赛材料要求"源代码（含 README 和测试用例）"。很多队伍把"测试用例"理解为几张手写文档。本方案的理解是：**测试用例是安全主张的证据**。

我在文档里写"角色天花板不可逾越"，评委凭什么信？凭 `只读角色转账 → 拒绝（POL-ROLE-CEILING）` 这条可运行的用例。

### 6.2 用例组织

64 条，分 7 组：

| 组 | 条数 | 关注点 |
|---|---|---|
| L1 注入防御 | 9 | 6 类攻击 + 变体 + 误杀率 |
| L2 意图解析 | 11 | 槽位、单位、歧义、拒绝清单 |
| L3 权限分级 | 13 | 三角色 × 四等级 × 环境因素 |
| L4 幻觉防护 | 5 | 溯源、虚构检出、异常处理 |
| L5 双智能体 | 6 | 各规则命中、否决权归属 |
| 审计链 | 2 | 连续性、篡改检出 |
| 端到端 | 8 | 每层短路位置正确 + 缺槽位不进入执行链路 |

另有 `tests/e2e.js` 做 31 条流程模拟（含三角色切换），验证从输入到裁决分支的完整控制流不抛异常，定位到"场景编码为 undefined"这类只能通过联调发现的缺陷；`tests/dom.test.js` 做 26 条 DOM 集成测试（jsdom 真实加载页面，验证渲染与交互）。三套断言共 **121 条**，与 CI 工作流（`.github/workflows/tests.yml`）完全一致。

### 6.3 开发过程中测试实际抓到的问题

如实记录，这是测试价值的证明：

| 问题 | 现象 | 修复 |
|---|---|---|
| 金额解析漏判 | "转 200 给 13912345678" 金额为 null | 手机号先替换为占位符，避免数字被整体吞掉 |
| 单位丢失 | "200 万" 只解析出 200 | 万/千/k 单位不再强制要求"元" |
| 意图误判 | "给妈妈和王大川转账 500" 判为 UNKNOWN | 改为句式优先 + 并列结构兜底 |
| 备注未提取 | 涉诈话术在正文中，未进 `action.note` | 增加「备注：」显式提取 + 原文透传 |
| 老人规则失效 | R-05 逻辑上永远不触发（变量 `h` 未参与） | 去掉无用条件，改为组合特征判定 |
| 缺槽位穿透 | "我要转账"无收款人无金额，却走到了二次认证，`payee` 为 null 会进执行器 | L2 增加槽位完整性检查，缺槽位直接 CLARIFY |
| 时间窗口数字漏进校验 | 账单回复"近 30 天"里的 30 不在证据集，L4 校验恒失败、恒标黄 | 时间窗口改为 `{G}` 占位符注入，30 与台账数字一样必须有出处 |
| 快捷按钮名落到查询 | 界面上的「＋ 申请虚拟卡」点下去只返回卡片清单——「卡」这个单字别名先于「申请/开卡」命中，把一次 R3 办卡降级成了 R0 查询 | 补齐 `申卡/开卡/申请…卡` 语义，并新增一条直接读 `index.html` 里按钮数组的用例 |
| 缺槽位提示 undefined | 「每月 800 元」缺储蓄目标，界面显示「我需要再确认一下：undefined」 | `MISSING_SLOT` 分支补上 `hint`，并给出可照抄的例句 |
| 弹窗关闭后焦点丢失 | 关掉二次认证弹窗，焦点落在 `body` 上，用户接着打字全落空——体感就是"请求发不出去" | `closeModal()` 关闭时把焦点还给输入框 |
| 遮罩期间请求被吞 | 弹窗开着时发送，请求在遮罩背后跑完，用户只看到"没反应" | `UI.send` 先收弹窗再起管线；运行期加 busy 互斥与「处理中」态 |

第 5 条尤其值得说：如果不是写测试，这条规则会一直"存在但不生效"——这在安全系统里是最危险的一类缺陷，因为评审看到规则表会以为有防护，实际是空的。

第 6 条是流程模拟（`tests/e2e.js`）抓到的，单元测试抓不到——因为单元测试分别测了"解析出 missing"和"策略决策"，都对，但没测"missing 之后管线是否短路"。这类缺陷只能靠端到端模拟暴露。

后四条来自一次真实的使用反馈：「请求发不出去」。用 CDP 接管真实浏览器逐条复现后，问题不在发送按钮本身——按钮可点、回车可用、零异常——而是**三条会让人以为它坏了的状态路径**：焦点丢了、遮罩把请求盖住了、文案吐了个 undefined。这类问题的教训是：**"没反应"从来不是一个 bug，而是一组状态没被收干净**。

### 6.4 一致性保证

`tests.html`（浏览器）与 `tests/run.js`（命令行）共用 `tests/testcases.js`，不维护两份用例。避免"演示环境通过、CI 环境失败"这类常见不一致。

## 7. 工程决策记录

### 决策 1：零依赖、零构建

**取舍**：放弃组件化、放弃 TypeScript 类型安全、放弃现代框架的开发效率。

**理由**：决赛现场网络不可控。一个双击即可运行、断网可用的作品，可靠性远高于需要 `npm install` 的工程。此外，评委审阅源码时，单文件无构建步骤能显著降低理解成本。

**代价与缓解**：用 IIFE 模块模式（`const X = (() => {...})()`）保持模块边界清晰，用 JSDoc 注释补充类型信息。

### 决策 2：规则 NLU 而非大模型 NLU

**取舍**：牺牲自然语言理解的广度。

**理由**：可解释性 + 可测试性 + 零成本。在"安全性"权重 30% 的赛题下，把 NLU 做成黑盒反而削弱了论点——因为"模型判断"无法作为安全证据。

**演进路径**：前置小模型做意图分类（提高召回），规则层保留为后置校验（保证下限）。这个混合架构可以在黑客马拉松阶段实现。

### 决策 3：安全引擎与 UI 彻底解耦

**取舍**：需要自己实现一套轻量的 UI 状态同步。

**理由**：这是能写 Node 测试的前提。如果安全判断散落在 UI 代码里，就永远无法做自动化回归。

## 8. 可扩展方向（黑客马拉松阶段可做）

| 方向 | 工作量 | 价值 |
|---|---|---|
| 接入小模型做意图分类（前置 classifier） | 中 | 解决 R1 风险，提升 NLU 鲁棒性 |
| 审计链换成 SHA-256 + Web Crypto 异步管线 | 小 | 解决 R2，达到生产可用 |
| 增加"家庭守护"模式：老人账户异常时通知子女 | 中 | 场景延展，社会价值强 |
| 交易流水可视化（近 90 天趋势图） | 小 | 账单分析体验提升 |
| 语音全双工对话（当前为单轮语音输入） | 大 | 体验提升 |

**建议优先级**：审计链 SHA-256（小成本补齐硬伤）> 家庭守护模式（差异化叙事）> 小模型分类器。

---

## 9. 结语

这个作品想证明的一件事是：**在"AI 代人操作银行"这个命题下，安全不是给功能加锁，而是功能的一部分。**

因为一旦 Agent 有了账户权限，它的"能力"和"风险"就是同一个东西的两面。设计得好的 Agent，应该在用户说"转 8 万给这个新账户"时，不是显示一个黄色感叹号，而是说"这笔我不能直接执行，原因是……，如果你确认，请走这条路"。

FinGuard 就是想把这件反直觉的事，做成一个能当场演示、能当场测通的系统。
